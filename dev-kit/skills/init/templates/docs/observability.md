# Observability

> Tests prove the behaviour you asserted holds; observability is **whether you can still see what happened when something goes wrong**. With no convention for where to instrument and at what level, you get one of two extremes: nothing logged (guesswork when it breaks), or everything logged (zero signal-to-noise, which amounts to the same).
>
> It is also a **verification and reproduction tool** — see [below](#verifying-and-reproducing-with-observability-data) and [`verification.md`](./verification.md).

### How to choose a level

**A level is a filter for the reader, not an emphasis marker for the author.**

| Level | When to use it | Criterion | Counter-example |
|---|---|---|---|
| `ERROR` | Something failed and **needs a human** | Its appearance should mean someone goes and looks | Invalid user input — a normal business branch |
| `WARN` | Degraded, retried, hit a fallback, **but still working** | Nothing is broken now, but **repeated occurrences are a problem** | Anything emitted on every request |
| `INFO` | A **milestone** in a key business event | On by default in production; what you reconstruct "what happened" from | Inside a loop, or on every function entry/exit |
| `DEBUG` | Intermediate state needed only while investigating | Off by default; once enabled, enough to locate the problem | Sensitive data (**banned at every level**) |

- **An `ERROR` must be actionable.** One nobody will act on trains everyone to ignore `ERROR`, and then the real incident drowns. If no human is needed, demote it.
- **Having logged an `ERROR`, do not also rethrow the same error** (or vice versa), or one failure gets recorded three times up the call chain. **Log it once, at the layer that can decide the thing failed.**

### Where to instrument

**Instrument by "event", not by function** — the places where, if something goes wrong, you will want the input, the output and the duration:

| Place | What to log | Level |
|---|---|---|
| **External call boundaries** — third-party APIs, database connections, publishing | Target, key parameters, duration, success/failure | `INFO`/`DEBUG`; `WARN`/`ERROR` on failure |
| **State changes** — creating/updating/deleting a key entity | Entity id, key fields before and after, the actor | `INFO` |
| **Permission and security decisions** | Subject, resource, decision, basis | `INFO` (`WARN` for a denial) |
| **Failure paths and degradations** — retries, circuit breaking, fallbacks, timeouts | Reason, which retry, what it degraded to | `WARN` |
| **Long-running task lifecycles** | Task id, parameter summary, duration, result | `INFO` |
| **Cross-process / cross-layer entry and exit** — <this project's boundaries> | Request identifier, key parameters | `DEBUG`/`INFO` |

**What not to log:** inside a loop, on every function entry/exit, getters/setters; anything derivable from the next line of code; **sensitive data**.

### Message and field format

- **Messages use the fixed prefix `<package.Method:>`**, making the source greppable.
- **Dynamic values go into structured fields, not concatenated into the string** — concatenated, they cannot be filtered or aggregated.

```<language>
// ✅ structured — this project's own wrapper, prefix and field names
<logger.Ctx(ctx).Info("client.Connect: connected", zap.String("target_id", id), zap.Duration("cost", d))>

// ❌ concatenation — cannot be filtered or aggregated by target_id
<logger.Info(fmt.Sprintf("connected to %s in %v", id, d))>
```

- **Carry a correlation id** (<request id / trace id / session id / task id>). **Logs with no correlation id are nearly unreadable under concurrency.**

### What must never reach the logs (a hard red line)

**Passwords, tokens, secrets, cookies, private keys, complete credentials, personally identifying information, payment information, and complete request/response bodies.**

- Where an identifier is needed, use a **redacted form**: `<user_id rather than a phone number>`, `<the first 6 characters of a token + its length>`, `<the redaction function>`.
- Logs reach log files, log systems, issue attachments and an AI's context — **far more readers than you imagine.**
- **This one can be pinned into a guardrail**: ban passing particular field names or types straight into the logger.

## Metrics

**Worth adding when it answers "how many / how fast / what proportion failed".** Facts about a single occurrence go in logs; **trends and distributions go in metrics**. The criterion: **would you want to see this number's curve over time?**

Start from the **four golden signals** rather than dozens of metrics up front:

| Signal | Metric | Type |
|---|---|---|
| **Traffic** | <call count of key operations> | Counter |
| **Errors** | <failure count, classified by reason> | Counter |
| **Latency** | <duration distribution of key operations> | Histogram |
| **Saturation** | <connection pool usage / queue length / concurrency> | Gauge |

- Consistent naming: `<project prefix>_<subsystem>_<object>_<unit>`.
- **A label's values must come from a bounded set** — high-cardinality values (`user_id`, `url`, `error_message`) blow up the time-series database and belong in logs.
- Failures must be classifiable **by reason** (timeout / rejected / network / internal), or "the error rate went up" leads nowhere.

## Verifying and reproducing with observability data

### When reproducing a bug

1. **Turn the log level up to `DEBUG` first** (<environment variable / config entry / switch>).
2. Walk through the reproduction steps.
3. **Pull out every log line for this one operation by correlation id**:

```bash
<command that filters logs by correlation id>
```

4. **Paste the decisive lines into the report**, not the whole log — see [`references/verification-report-template.md`](./references/verification-report-template.md).

**When it cannot be reproduced, the logs are the primary basis for "how far did it actually get"** — saying where it got to and which branch it did not enter beats saying "cannot reproduce".

### When verifying a change

**For what the UI cannot drive — background jobs, async flows, paths with no UI — verify through logs and data as observable side effects:**

- Assert that **a specific structured log line appeared** (not "no errors").
- Assert that **a metric changed as expected**.
- Cross-check with an independent oracle (the database, an output file) — see [`../e2e/README.md`](../e2e/README.md).
