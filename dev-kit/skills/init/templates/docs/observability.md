# Observability

> **Why it belongs to the constraint system.** Tests prove the behaviour you asserted holds; observability is **whether you can still see what happened when something goes wrong, in production and locally**. Without conventions for where to instrument and at what level, the result is always one of two extremes: nothing is logged (leaving you to guess when something breaks), or everything is logged (a signal-to-noise ratio of zero, which amounts to the same thing).
>
> It is simultaneously a **verification and reproduction tool** — see [Verifying and reproducing with observability data](#verifying-and-reproducing-with-observability-data), and [`verification.md`](./verification.md).

### How to choose a level

**A level is a filter for the reader, not an emphasis marker for the author.** The criterion is "who needs to see this, and when":

| Level | When to use it | Criterion | Counter-example |
|---|---|---|---|
| `ERROR` | Something failed and **needs a human** | Its appearance should mean someone goes and looks; putting it in an alert is reasonable | Invalid user input (that is a normal business branch; use `INFO`/`DEBUG`) |
| `WARN` | Degraded, retried, hit a fallback, **but still working** | Nothing is broken now, but **repeated occurrences are a problem** | Anything emitted on every request (that is `INFO`) |
| `INFO` | A **milestone** in a key business event | On by default in production; what you reconstruct "what happened" from afterwards | Inside a loop, or on every function entry and exit |
| `DEBUG` | Intermediate state needed only while investigating | Off by default in production; once enabled, there should be enough to locate the problem | Sensitive data (**banned at every level**) |

**Two hard rules:**

- **An `ERROR` must be actionable.** An `ERROR` nobody will act on trains everyone to ignore `ERROR` — and then the real incident drowns. If no human is needed, demote it to `WARN`.
- **Having logged an `ERROR`, do not also rethrow the same error** (or vice versa), or one failure gets recorded three times up the call chain. **Log it once, at the layer that can decide "this thing failed".**

### Where to instrument (the high-value places)

**Instrument by "event", not by function.** The places worth instrumenting share a characteristic: **when something goes wrong you will want to know its input, its output and how long it took.**

| Place | What to log | Level |
|---|---|---|
| **External call boundaries** — third-party APIs, database connections, publishing messages | Target, key parameters, duration, success/failure | `INFO`/`DEBUG` on success, `WARN`/`ERROR` on failure |
| **State changes** — creating/updating/deleting a key entity | Entity id, key fields before and after, the actor | `INFO` |
| **Permission and security decisions** — authentication, authorisation, denial | Subject, resource, decision, basis | `INFO` (`WARN` for a denial) |
| **Failure paths and degradations** — retries, circuit breaking, fallbacks, timeouts | Reason, which retry, what it degraded to | `WARN` |
| **Long-running task lifecycles** — start / progress / finish | Task id, a parameter summary, duration, result | `INFO` |
| **Cross-process / cross-layer entry and exit** — <this project's specific boundaries> | Request identifier, key parameters | `DEBUG`/`INFO` |

**What not to log:**

- Inside a loop, on every function entry and exit, getters/setters.
- Anything derivable from the next line of code (`log("starting"); process();`).
- **Sensitive data** — see below.

### Message and field format

- **Messages use the fixed prefix `<package.Method:>`**, making the source greppable.
- **Dynamic values go into structured fields rather than being concatenated into the string** — concatenated, they cannot be filtered or aggregated on.

```<language>
// ✅ structured — replace with this project's own wrapper, prefix and field names
<logger.Ctx(ctx).Info("client.Connect: connected", zap.String("target_id", id), zap.Duration("cost", d))>

// ❌ string concatenation — cannot be filtered or aggregated by target_id
<logger.Info(fmt.Sprintf("connected to %s in %v", id, d))>
```

- **Carry a correlation id**: <request id / trace id / session id / task id>. **Logs with no correlation id are nearly unreadable under concurrency** — you cannot tell which lines belong to the same operation.

### What must never reach the logs (a hard red line)

**Passwords, tokens, secrets, cookies, private keys, complete credentials, personally identifying information, payment information, and complete request/response bodies (which may carry any of the above).**

- When an identifier is needed, use a **redacted form**: `<user_id rather than a phone number>`, `<the first 6 characters of a token + its length>`, `<the redaction function>`.
- Logs reach log files, log systems, issue attachments and an AI's context — **they have far more readers than you imagine.**
- **This one can be pinned into a guardrail**: ban passing particular field names or types straight into the logger.

## Metrics

### When it is worth adding

**When it answers "how many / how fast / what proportion failed".** Facts about a single occurrence go in logs, while **trends and distributions go in metrics** — computing trends from logs is using the log system as a database, which is both expensive and slow.

The criterion: **would you want to see this number's curve over time?** Yes → a metric; looked at once when something breaks → a log.

### Which ones to emit

Start from the **four golden signals**, rather than laying down dozens of metrics up front:

| Signal | Metric | Type |
|---|---|---|
| **Traffic** | <call count of key operations> | Counter |
| **Errors** | <failure count, classified by reason> | Counter |
| **Latency** | <duration distribution of key operations> | Histogram |
| **Saturation** | <connection pool usage / queue length / concurrency> | Gauge |

### Naming and labels

- Consistent naming: `<project prefix>_<subsystem>_<object>_<unit>`, e.g. `<myapp_db_query_duration_seconds>`.
- **A label's values must come from a bounded set.** Turning **high-cardinality** values like `user_id`, `url` or `error_message` into labels blows up the time-series database — those belong in logs.
- Failures must be classifiable **by reason** (timeout / rejected / network / internal), or "the error rate went up" leads nowhere.

## Distributed tracing

### When it is worth adding

**When one user operation spans several services / processes / async tasks.** In a single-process monolith, structured logs + a correlation id are already enough, and tracing is extra complexity.

The criterion: **can you follow one operation through every component using a single identifier?** If not, and you need to often → adopt tracing.

### How to use it

- **Draw spans at meaningful boundaries**: an external call, a database query, an async task — largely coinciding with the high-value places under "where to instrument" above.
- **Context must be passed all the way down.** A broken context breaks the trace, and the rest becomes orphan spans. <This project's convention for passing context>.
- **The trace id goes into a log field** — that is the only bridge from "one log line" to "the complete trace", and the one place tracing and logging must be joined.

## Verifying and reproducing with observability data

**This is observability's most direct return for day-to-day development, and an important technique in [`verification.md`](./verification.md).**

### When reproducing a bug

1. **Turn the log level up to `DEBUG` first** (<how: environment variable / config entry / switch>).
2. Walk through the reproduction steps.
3. **Pull out every log line for this one operation by correlation id**:

```bash
<command that filters logs by correlation id, e.g. grep / jq>
```

4. **Paste the decisive lines into the report**, not the whole log — see [`references/verification-report-template.md`](./references/verification-report-template.md).

**When it cannot be reproduced, the logs are the primary basis for judging "how far did it actually get"** — saying where it got to and which branch it did not enter is far more useful than saying "cannot reproduce".

### When verifying a change

**For things the UI cannot drive (background jobs, async flows, paths with no UI), verify through logs and data as observable side effects** — this is how `AGENTS.md`'s "**verify by observing, not by asserting**" lands in practice:

- Assert that **a specific structured log line appeared** (not "no errors").
- Assert that **a metric changed as expected**.
- Cross-check with an independent oracle (querying the database / an output file) — see [`../e2e/README.md`](../e2e/README.md).
